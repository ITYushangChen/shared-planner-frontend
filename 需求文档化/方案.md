# ShareTodo AI 实施方案

> 对照文档：《项目需求.docx》  
> 数据库脚本：`supabase/migrations/20260804000000_init_sharetodo.sql`

本文说明 **做什么、怎么做、为什么这么做**，作为开发与验收依据。

---

## 一、目标与成功标准

**产品目标**：面向小团队 / 家庭 / 密友，在同一「空间」内用「待办 + 日历时间段」协同，并用自然语言驱动任务创建与时间规划。

| 验收场景（需求典型路径） | 判定标准 |
|--------------------------|----------|
| 建空间并邀请成员 | 多人进入同一空间，角色正确 |
| 一句话生成多条带时间的待办 | 标题 / 指派 / 时段解析正确并入库 |
| 日历月 / 周 / 日看到各自安排 | 拖拽改期后全员可见 |
| 同一人时段重叠 | 红色冲突标记；（加分）AI 调整建议 |
| 未排期侧栏 | `start_at` 为空的待办单独展示 |
| 每日摘要 | 按日推送可读摘要到通知 |

---

## 二、技术选型与原因

| 层级 | 建议 | 原因 |
|------|------|------|
| 后端 / DB | **Supabase**（Postgres + Auth + RLS） | 需求为邮箱密码 + JWT；多租户用 RLS 比纯应用层鉴权更安全；迁移脚本已就绪 |
| 前端 | **Next.js（App Router）+ TypeScript** | Web 一套代码；路由清晰；易接 Supabase SSR |
| 日历 UI | **FullCalendar** 或同类周/日视图库 | 拖拽是核心交互；成熟库可显著缩短工期 |
| AI | **Supabase Edge Function + LLM API** | 密钥不能放前端；需带空间成员上下文解析并写库 |
| 实时（可选） | Supabase Realtime | 拖拽改期后他人日历即时刷新 |

**不建议一上来做**：独立自建后端、自签 JWT、把排期拆成第二套日历表——会拖慢 MVP，且与「每个待办绑定一个时间段」不一致。

---

## 三、整体架构

```text
┌─────────────┐     JWT      ┌──────────────────┐
│  Web App    │─────────────▶│  Supabase Auth   │
│  (Next.js)  │              └────────┬─────────┘
│             │                       │ auth.users
│  列表/日历  │              ┌────────▼─────────┐
│  拖拽/筛选  │──── CRUD ───▶│  Postgres + RLS  │
│             │              │  profiles/spaces │
│  AI 输入框  │── invoke ───▶│  todos / …       │
└─────────────┘              └────────┬─────────┘
                                      │
                             ┌────────▼─────────┐
                             │ Edge Functions   │
                             │ ai-parse         │
                             │ ai-schedule      │
                             │ daily-summary    │
                             └──────────────────┘
```

**原因**：

- 常规 CRUD 走带 RLS 的客户端直连：快、少胶水代码。
- AI、邀请核销、定时摘要等「要保密钥或跨用户写」的能力走 Edge Function / RPC。

## 四、数据模型对照

现有 11 张业务表已覆盖五大需求模块。

| 需求模块 | 表 / 对象 | 设计原因 |
|----------|-----------|----------|
| 注册登录 | `auth.users` + `profiles` | 密码交给 Auth；昵称 / 时区放业务表 |
| 多空间 | `spaces` + `space_members` | 用户↔空间多对多，支持切换 |
| 邀请 | `space_invitations` + RPC `accept_invitation` | 次数 / 过期用事务校验，避免前端绕过 |
| 待办 + 日历 | `todos.start_at` / `end_at` / `is_all_day` | 需求是「每待办一个时间段」，不必再拆事件表 |
| 多人指派 | `todo_assignees` | 场景含「全员」「小李+小王」 |
| 评论 | `todo_comments` | 协作沟通 |
| AI | `ai_conversations` / `ai_messages` / `ai_actions` | 可审计、可撤销 |
| 摘要 / 提醒 | `notifications` | 每日推送落库 |
| 冲突检测 | RPC `check_schedule_conflicts` + `time_range` | 区间重叠用数据库判断更稳 |
| 所有权转让 | RPC `transfer_space_ownership` | 创建者退出前须转让 |

### 4.1 执行数据库脚本

1. 打开 `supabase/migrations/20260804000000_init_sharetodo.sql`
2. **全选复制 SQL 正文**（不要复制文件路径）
3. 粘贴到 Supabase → SQL Editor → Run
4. 在 Table Editor 确认表已创建

> 脚本开头含 `DROP`，重复执行会清空业务表数据；`auth.users` 不会删除。

## 五、分阶段实施计划

### Phase 0：地基（约 0.5–1 天）

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | 创建 Supabase 项目并执行 migration | 后续功能依赖统一 schema |
| 2 | 配置 Auth：Email / Password（开发期可关闭邮箱确认） | 对齐「邮箱 + 密码」；加快联调 |
| 3 | 前端工程配置 `NEXT_PUBLIC_SUPABASE_URL` / `ANON_KEY` | 客户端只用 anon key + RLS |
| 4 | 注册联调：检查 `profiles`、个人空间、`role=owner` | 验证 Trigger `handle_new_user` |

---

### Phase 1：账号与空间（模块 1 + 5）

**目标**：多租户空间闭环可用。

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | 登录 / 注册页（`signUp` / `signIn`） | Auth 是所有 RLS 的前提（`auth.uid()`） |
| 2 | 顶栏空间下拉：`space_members` join `spaces` | 多空间切换是全局上下文 |
| 3 | 当前空间存 URL 参数或 `localStorage` | 刷新后保持 `space_id` |
| 4 | 空间设置：修改名称 / 头像 / 描述 | RLS 已限制 owner / admin |
| 5 | 生成邀请：写入 `space_invitations` | 一次性、有效期用表字段表达 |
| 6 | 加入空间：调用 `accept_invitation` | SECURITY DEFINER 安全校验 |
| 7 | 成员列表、移除、转让所有者 | 满足「退出前须转让」 |

**建议路由**：

- `/login` `/register`
- `/app`（应用壳）
- `/app/settings/space`
- `/invite/[code]`

---

### Phase 2：待办 CRUD 与列表（模块 2）

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | 表单：标题、描述、优先级、状态、指派人多选 | 指派人仅来自当前空间成员 |
| 2 | 写入 `todos` + `todo_assignees` | 避免「有任务无指派」 |
| 3 | 列表按状态 / 指派人 / 优先级筛选排序 | 需求明确；索引已按 space 维度建立 |
| 4 | 完成时写 `completed_by` / `completed_at` | 协作可追溯 |
| 5 | 评论时间线 `todo_comments` | 先满足沟通，不做复杂动态表 |

**原因**：先验证数据模型，日历只是同一批 `todos` 的另一种视图。

---

### Phase 3：日历与冲突（模块 3，产品差异点）

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | 月 / 周 / 日视图；按可视范围查 `start_at`～`end_at` | 视图层过滤，无需独立事件表 |
| 2 | 侧栏「待排期」：`start_at IS NULL AND status <> done` | 与部分索引一致 |
| 3 | 拖拽更新 `start_at` / `end_at`（乐观更新 + 失败回滚） | 需求核心交互，精确到分钟 |
| 4 | 全天事件：`is_all_day = true`，渲染在日顶 | 与时段任务视觉分离 |
| 5 | 冲突：调用 `check_schedule_conflicts`，重叠标红 | `tstzrange` 重叠判断可靠 |
| 6 | （可选）Realtime 订阅 `todos` | 改期后团队即时同步 |

**产品建议**：从待排期拖入日历 = 首次写入时间段；支持清空时间段回到待排期。

---

### Phase 4：AI 智能能力（模块 4）

按价值顺序实现。

#### 4.1 自然语言创建待办（必做）

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | Edge Function `ai-create-todos`（入参：文本 + `space_id`） | 密钥与 Prompt 不暴露 |
| 2 | Function 内拉取成员（`display_name` → `user_id`） | 「小明」必须映射到真实用户 |
| 3 | LLM 输出严格 JSON（标题、优先级、指派、时段、截止） | 结构化才能可靠写库 |
| 4 | **先预览，用户确认后再写入** | 降低误解析污染日历 |
| 5 | 写入后记 `ai_actions`（`create_todo`） | 可审计、可撤销 |

#### 4.2 智能排期

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | 取未排期任务 + 成员已有 `time_range` | 「忙闲」来自真实日程 |
| 2 | 规则引擎找空档为主，LLM 只做说明 | 空档算法确定；纯 LLM 易乱排 |
| 3 | 建议确认后再 `update` | 与 4.1 同一人机共审原则 |

#### 4.3 智能重排序

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | 用优先级 + 截止临近度计算 `sort_score` | 需求要「紧急且临近置顶」；可先无 LLM |
| 2 | 列表按 `sort_score DESC` | 成本低、结果稳定 |

#### 4.4 每日智能摘要

| 步骤 | 做法 | 原因 |
|------|------|------|
| 1 | 定时任务调用 Edge Function | 「早上自动推送」需要调度 |
| 2 | 按 `profiles.timezone` 筛当日待办 → 写入 `notifications` | 跨时区正确 |

#### 4.5 冲突解决建议（加分）

冲突检出后，将冲突任务与优先级交给 LLM，返回「挪哪个到几点」；写入 `ai_actions`（`conflict_suggest`），支持一键应用。

## 六、前端信息架构

```text
/app
  ├─ 顶栏：空间切换 | 通知铃铛（每日摘要）
  ├─ 左：待排期列表（可拖拽）
  ├─ 中：日历（月 / 周 / 日）
  ├─ 右或抽屉：待办详情（编辑、指派、评论）
  └─ 全局：AI 输入框「用一句话创建 / 排期」
```

**原因**：

- 需求以日历为协同主视图。
- 待排期必须常驻，否则「任务 + 时间」闭环断裂。
- AI 入口全局可达，才符合「全程赋能」。

---

## 七、接口与调用约定

| 能力 | 调用方式 | 原因 |
|------|----------|------|
| 登录注册 | `supabase.auth.*` | 官方 Auth |
| 空间 / 待办 / 评论 | `from('…').select/insert/update` | RLS 已覆盖 |
| 接受邀请 | `rpc('accept_invitation')` | 复杂校验集中在 DB |
| 转让所有者 | `rpc('transfer_space_ownership')` | 双表原子更新 |
| 冲突检测 | `rpc('check_schedule_conflicts')` | 区间逻辑集中 |
| AI | `functions.invoke('ai-create-todos')` 等 | 密钥与多步写库 |

**安全原则**：

1. 永不把 `service_role` 放前端。
2. 业务查询始终带当前 `space_id`，并由 RLS 校验成员身份。
3. 加入空间只走邀请 RPC，避免伪造成员写入。
4. AI 写库前校验指派人必须属于当前空间。

## 八、测试清单

1. 注册 → 自动创建个人空间且角色为 owner  
2. A 邀请 B → B 调用 `accept_invitation` → 双方可见同一空间待办  
3. 创建未排期 → 侧栏出现 → 拖到周三 14:00–16:00 → 日历可见  
4. 同一人重叠两任务 → 标红；RPC 返回冲突记录  
5. 输入「明天下午2点到4点和小明做需求评审，高优先级」→ 预览正确 → 确认入库  
6. Owner 转让后：原 owner 变为 member，新 owner 可管理成员  
7. 全天事件展示在日历顶部；完成待办记录完成人与时间

## 九、推荐工期（1–2 人）

| 周次 | 交付 | 原因 |
|------|------|------|
| 第 1 周 | Phase 0–1 + 待办列表 | 没有空间上下文，后续全白做 |
| 第 2 周 | 日历拖拽 + 待排期 + 冲突标红 | 产品差异点，尽早可演示 |
| 第 3 周 | AI 自然语言建待办（确认后写入） | 主打卖点；先创建再排期 |
| 第 4 周 | 智能排期 / 重排序 + 每日摘要 + 体验打磨 | 粘性与加分项 |

## 十、立即执行的三件事

1. **确认 migration 已在 Supabase 跑通**（能看到 `profiles`～`notifications`）。  
2. **搭前端并接好 Auth + 空间切换**（全局持有当前 `space_id`）。  
3. **先做待办列表 + 简易周视图，再接 AI**——避免主路径被 Prompt 工程卡住。
